# WeChat 网关限流应对策略

> 📅 最后更新: 2026-05-16 | 来源: 用户江玉婷(Keke)提供的系统指南，结合hermes-agent实际运行经验

## 体系全景图：限流是个人微信接AI的第一道坎

Hermes接入微信被限流，是从个人娱乐迈向严肃生产力的必经之路。这不代表做错了什么，而是Hermes的主动保护机制在帮你规避封号风险。

```
限流应对 → 分四步走：
① 认清你的路线（个人微信 vs 企业微信）
② 判断你在哪条路上
③ 执行对应的策略
④ 通用法宝 + 终极建议
```

---

## 第一步：认清路线 — 个人微信 vs 企业微信

| 对比维度 | 个人微信 (WeChat/iLink) | 企业微信 (WeCom) |
|----------|------------------------|-----------------|
| 接入性质 | iLink Bot API — 腾讯官方bot接口，非逆向。中等风险 | 官方开放API，合规稳定 |
| 常见报错 | ret=-2 / errmsg="rate limited" | HTTP 429, 错误码45009 |
| 限流阈值 | 无公开文档，风控靠行为模式（回复速度/内容随机性），滑动窗口 | 公开限额：每应用20 QPS，10000次/分钟 |
| 应对核心 | 让行为看起来像真人 | 管理好请求频率 |

**核心建议**：关键业务用企业微信API。个人微信注意控制节奏，务必用小号。

---

## 第二步：判断你在哪条路上

- **个人微信（iLink API）**：通过 `hermes gateway setup` 的微信配置向导扫码登录。代码在 `gateway/platforms/weixin.py`，使用 `ilinkai.weixin.qq.com` 接口
- **企业微信（官方API）**：在企业微信后台创建应用，获取 CorpID/AgentID/Secret，通过 `hermes gateway setup` 选择 WeCom

---

## 第三步：执行对应策略

### 🛡️ 对策A：个人微信限流优化

核心策略：**慢 + 随机 + 像真人**

#### 1. 降低消息频率
目前 weixin.py 中有：
- `RETRY_DELAY_SECONDS = 2` — 重试间隔
- `BACKOFF_DELAY_SECONDS = 30` — 退避时间
- `RATE_LIMIT_ERRCODE = -2` — 限流错误码
- `_is_stale_session_ret()` — 区分真正限流 vs 过期会话

建议：在 `config.yaml` 中增加消息发送速率的全局控制参数（如果后续支持）。

#### 2. 引入随机延迟
手动发送消息时：
- 3-5秒间隔是最低安全线
- 避免固定节律（如每3秒发一条——太规律了）
- 观察到的限流触发窗口：5-10条消息在<60秒内

#### 3. 内容随机化
- 避免相同内容连续高频发送
- 回复末尾可加动态时间戳或变化的内容

#### 4. 新IP"预热"
- 更换服务器/IP后，前72小时以保持在线为主，不进行高频互动
- 登录后先静置一段时间再发消息

#### 5. 登录设备
- 确保微信账号未在其他设备（PC、平板）同时登录，可能强制下线
- 微信PC版和iLink bot可以同时在线，但注意不要出现消息风暴

### 🏢 对策B：企业微信API（当前未使用，未来参考）

- 调整 `~/.hermes/gateways/wecom/config.json` 中 `requests_per_second` 至 5 或更低
- 系统默认 `retry_backoff_ms: 2000`
- 使用令牌桶算法限流
- 实现指数退避重试：`2^attempt` 秒
- 多应用分流、消息队列错峰
- 熔断机制：连续限流时自动暂缓发送

## 第四步：通用法宝

### 理解"滑动窗口"

微信风控使用滑动窗口（sliding window），而非固定每分钟重置。举例：

```
10:00:00 - 10:00:30  → 发18条
10:00:30 - 10:01:00  → 发18条
10:01:00 - 10:01:30  → 发18条
```

固定分钟看似安全（每分钟18条），但在滑动窗口下：
- 10:00:30 至 10:01:30 这个60秒窗口 → **36条**，严重超限！

**要求**：请求间隔在时间轴上均匀分布，避免规律性峰值。

### 诊断命令

```bash
# 自动诊断
hermes doctor

# 网关日志排查
grep -i "rate\|429\|-2\|limit\|error" ~/.hermes/logs/gateway.log | tail -30

# 监控API调用量（如果支持）
hermes gateway metrics
```

### 限流后恢复流程

1. 检测到 `ret=-2 errmsg="rate limited"` → **立即停止发送**
2. 等待至少5分钟（实测限流时长可能更长）
3. 恢复后先发一条测试消息，确认正常再继续
4. 恢复后降低频率（建议拉到5-8秒间隔）

## 合规框架：微信个人账号使用规范关键条款

📅 规则版本：2026-04-29 | 来源：https://weixin.qq.com/agreement/personal_account

Hermes通过iLink API操作个人微信账号，以下条款直接相关：

### 与我们相关的核心条款

| 条款 | 内容 | 风险等级 |
|------|------|:--------:|
| **第1.2.6条** 自动化操作 | 禁止通过非腾讯授权软件/插件进行自动化操作或访问微信服务 | 🔴 高 |
| **第3.4条** 高频异常行为 | 禁止在一定期间内产生异常大量的信息或频繁加好友/加群/拉群 | 🟡 中-高 |
| **第12.3条** 骚扰及垃圾信息 | 禁止批量/高频发机器生成的内容，或引流到第三方 | 🟡 中 |
| **第1.2.9条** 违规示例 | 明确列出抢红包、多开、皮肤修改、一键转发等插件 | 🔴 高 |
| **第五条** 处理措施 | 阶梯处罚：删除违规信息→警告→限制功能→短期封号→永久封号→回收账号 | 🟡 参考 |

### 对我们实操的影响

- **我们做的是**：agent自动帮你收发消息、发文件、做通知——严格说属于第1.2.6条的"自动化操作"范围
- **但我们不做**：营销骚扰、批量加好友、拉群、引流、抢红包——这些是真正的高危行为
- **核心风险是频率**：机器人特征最容易被检测的点就是"非人类节奏"——固定间隔、无停顿、无随机性
- **iLink的ret=-2限流就是微信的风控在保护**：不是系统故障，是正常的安全机制在起作用

### 安全操作边界

```
✅ 可以做的                        ❌ 千万别做
────────────────────────────────────────────────────
• 给Keke发私人消息/文件            • 批量加陌生人好友
• 检查通知/回复消息                • 拉群发营销内容
• 定时任务结果通知                 • 自动抢红包
• 控制频率 (3-5秒间隔)             • 引流到第三方平台
• 发送MEDIA文件                    • 高频>1条/秒（触发滑动窗口）
```
